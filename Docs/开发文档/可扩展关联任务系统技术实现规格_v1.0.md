## 2. 唯一目标

把当前只能处理一条硬编码跨场景任务的 `WorldQuest` 实现，升级成数据驱动、可同时运行多条任务、支持任务结局、世界状态、前置条件、任务链、互斥、中断、恢复、失败和取消的 World Quest V2。

重构完成后，新增普通剧情任务必须满足：

1. 创建或复制一个 `WorldQuestDefinition` 资源。
2. 填写任务阶段、目标、条件、结局和效果。
3. 如需新对话，仅填写任务资源中的对话文本。
4. 不修改市场、战斗、地图、背包、`DialogueManager`、`WorldQuestRuntime` 或任务推进服务。

最低证明案例：

> 新增“给铁匠交付3块石头”的任务时，只新增任务资源和对应内容配置，不新增 `if (questId == ...)`，不修改任务核心代码。

## 3. 已确认的架构决策

以下决策在本轮固定，不再实现时临时选择。

### 3.1 两类任务的边界

项目当前有两套任务：

1. 旧 `QuestManager`：66个既有资源，主要是教程、数值里程碑和场景内挑战。
2. `WorldQuestRuntime`：跨地点叙事任务，目前只有“林间异响”。

本轮采用以下边界：

- World Quest V2 是所有新主线、支线、NPC委托、阵营任务和跨场景任务的唯一系统。
- 旧 `QuestManager` 只保留给现有66个教程和里程碑资源。
- 禁止新增旧 `Quest` 资源承载剧情。
- 本轮不迁移66个旧任务，不删除 `QuestManager`。
- `QuestsView` 必须同时显示两类任务，但必须分为“主线/支线”和“教程与里程碑”两个来源。
- 旧任务不得读取或修改 World Quest V2 的状态、结局和世界事实。
- World Quest V2 可以通过只读条件读取玩家等级、物品数量、世界日期等正式游戏数据，但不得读取旧任务的场景内临时对象。

### 3.2 任务流程模型

World Quest V2 使用：

```text
任务
└─ 阶段（Stage，有向无环图）
   ├─ 目标（Objective，一个或多个）
   ├─ 阶段进入效果
   ├─ 阶段完成效果
   └─ 条件转移（Transition）
      ├─ 前往另一个阶段
      └─ 到达任务交付
```

固定规则：

- 阶段图必须是有向无环图，禁止循环阶段。
- 每个阶段的目标使用“全部完成”或“任意一个完成”。
- 同一任务只允许一个当前阶段。
- 普通目标事件只影响当前阶段，不回填已离开的阶段。
- 任务结局只能在最终交付或自动结算时确定。
- 任务的不同结局通过 `OutcomeId` 永久记录。
- 跨任务影响通过“世界事实”或明确的任务状态效果实现。

### 3.3 关联任务模型

任务之间禁止在业务代码中直接互相调用。任务关联只能通过以下数据实现：

- 可用条件读取另一任务的状态。
- 可用条件读取另一任务的结局。
- 可用条件读取世界事实。
- 结局效果激活、中断、恢复、失败或取消另一任务。
- 结局效果写入世界事实，其他任务根据事实改变可用性或结局。

禁止：

```csharp
if (questId == "quest_a")
    CompleteQuestB();
```

必须表达为资源数据：

```text
EffectId: activate_followup
Type: ActivateQuest
TargetId: quest_b
```

### 3.4 一致性模型

- `GameData` 是跨场景任务、世界事实、任务结局和任务追踪状态的唯一权威来源。
- ScriptableObject 只保存定义，不保存运行时进度。
- 所有奖励和跨任务效果必须通过一次任务事务提交。
- 同一效果必须有稳定的幂等键，重复点击、重复事件或读档不得重复执行。
- 任务变更全部完成后只保存一次。
- UI、音效和通知只能在事务提交成功后触发。

## 4. 本轮范围

### 4.1 必须实现

- 多任务注册、查询和同时运行。
- 数据驱动阶段、目标、条件、转移、结局和效果。
- 任务状态：锁定、可接、进行中、中断、可交付、完成、失败、取消。
- 世界事实：布尔、整数和字符串。
- 任务前置条件、结局条件和世界事实条件。
- 手动接取和自动激活。
- 手动交付和自动结算。
- 一个任务的结局激活、中断、恢复、失败或取消其他任务。
- 中断后从原状态恢复，不丢失目标进度。
- 结局奖励和状态影响的事务化、回滚和幂等。
- 每日重复和冷却小时重复。
- 单一任务追踪。
- NPC 多任务聚合、可接/可交标记和任务选择。
- “林间异响”从硬编码迁移到 V2，玩家体验和数值保持不变。
- 旧 World Quest V1 存档迁移到 V2。
- 编辑器资源验证器和自动化测试。

### 4.2 本轮不做

- 图形化任务节点编辑器。
- 任意 C# 脚本或反射表达式作为资源条件。
- Lua、JavaScript 或自定义任务脚本语言。
- 联机共享任务。
- 程序随机生成完整剧情。
- 任务倒计时和现实时间限时活动。
- 一个任务同时处于多个阶段。
- 运行时热更新任务定义。
- 已发布任务 ID、阶段 ID、目标 ID、结局 ID 的自动重命名。
- 把66个旧教程/里程碑任务迁移到 V2。

## 5. 术语与 ID 规范

### 5.1 术语

| 术语 | 精确定义 |
| --- | --- |
| 定义 | `WorldQuestDefinition` 资源中的只读设计数据 |
| 状态 | `WorldQuestStateData` 中随存档变化的数据 |
| 阶段 | 一组当前可推进目标和离开该组的转移规则 |
| 目标 | 监听一种正式游戏事件并累计进度的最小单元 |
| 条件 | 无副作用的布尔判断 |
| 效果 | 事务内执行的一项数据变更 |
| 结局 | 任务进入 `Completed` 时记录的稳定 `OutcomeId` |
| 世界事实 | 由字符串键索引的布尔、整数或字符串世界状态 |
| 任务事务 | 同时提交任务状态、世界事实、背包和主角成长的原子操作 |
| 运行轮次 | 可重复任务从接受到终止的一次执行，使用 `RunNumber` 标识 |

### 5.2 ID 格式

所有 ID：

- 使用小写 ASCII。
- 单词间使用下划线。
- 不允许空格、中文、大小写混用。
- 发布后不可修改。
- 比较使用 `StringComparison.Ordinal`，区分大小写。

固定格式：

| ID | 格式 | 示例 |
| --- | --- | --- |
| QuestId | `{category}_{region}_{subject}_{nn}` | `story_riverbend_whispering_forest_01` |
| StageId | 任务内简短名称 | `prepare_supplies` |
| ObjectiveId | 阶段内行为名称 | `buy_food` |
| TransitionId | `{from}_to_{to}` | `prepare_to_travel` |
| OutcomeId | 结果语义 | `threat_reported` |
| EffectId | 效果语义 | `grant_acceptance_coins` |
| ConditionId | 条件语义 | `requires_forest_purified` |
| WorldFactKey | `{domain}.{subject}.{property}` | `forest.slime_nest.state` |
| ChoiceGroupId | `{quest}.{purpose}` 的短名称 | `slime_resolution` |
| ChoiceId | 选择语义 | `purify_slimes` |

QuestId 的 `{category}` 固定映射：`Main=story`、`Side=side`、`Contract=contract`、`Tutorial=tutorial`、`Hidden=hidden`。

### 5.3 ID 唯一范围

- `QuestId`：全项目唯一。
- `StageId`：单个任务内唯一。
- `ObjectiveId`：单个任务内唯一，不只要求阶段内唯一。
- `TransitionId`：单个任务内唯一。
- `OutcomeId`：单个任务内唯一。
- `EffectId`：单个任务内唯一。
- `ConditionId`：单个任务内唯一。
- `WorldFactKey`：全存档共享。

### 7.2 `WorldQuestDefinition`

目标字段必须为：

```csharp
[CreateAssetMenu(
    menuName = "StackCraft/World Quest V2",
    fileName = "WorldQuest_")]
public sealed class WorldQuestDefinition : ScriptableObject
{
    [SerializeField] private int schemaVersion = 2;
    [SerializeField] private string id;
    [SerializeField] private WorldQuestCategory category;
    [SerializeField] private int priority;
    [SerializeField] private string title;
    [SerializeField, TextArea(2, 6)] private string description;
    [SerializeField] private WorldQuestVisibility visibility;
    [SerializeField] private WorldQuestStartMode startMode;
    [SerializeField] private WorldQuestTurnInMode turnInMode;
    [SerializeField] private WorldQuestRepeatPolicy repeatPolicy;
    [SerializeField, Min(1)] private int cooldownHours = 24;
    [SerializeField] private bool defaultTracked;
    [SerializeField] private string giverNpcId;
    [SerializeField] private string acceptLocationId;
    [SerializeField] private List<string> turnInNpcIds = new();
    [SerializeField] private string entryStageId;
    [SerializeField] private WorldQuestConditionSet hardStartConditions;
    [SerializeField] private WorldQuestConditionSet availabilityConditions;
    [SerializeField] private WorldQuestConditionSet acceptConditions;
    [SerializeField] private List<WorldQuestEffectDefinition>
        onAcceptEffects = new();
    [SerializeField] private List<WorldQuestStageDefinition> stages = new();
    [SerializeField] private List<WorldQuestOutcomeDefinition> outcomes = new();
    [SerializeField] private WorldQuestDialogueDefinition dialogue;
}
```

字段规则：

- `schemaVersion` 本轮只能为 `2`。
- `priority` 越大，NPC任务列表和自动处理顺序越靠前；相同则按 `QuestId` 升序。
- `cooldownHours` 仅在 `CooldownHours` 时使用。
- `giverNpcId` 在 `ManualAccept` 时必填。
- `acceptLocationId` 为空表示任何地点均可接取；非空时必须严格匹配当前 `ActiveLocationId`。
- `turnInNpcIds` 在 `ManualNpc` 时至少包含一个 ID。
- `entryStageId` 必须引用 `stages` 中存在的阶段。
- `hardStartConditions` 是即使被 `ActivateQuest` 强制启动也必须满足的世界不变量。
- `availabilityConditions` 决定 `Locked` 是否变为 `Available`。
- `acceptConditions` 在玩家确认接取时再次检查，用于临时费用、地点状态或对话选择限制。
- `onAcceptEffects` 只在成功进入新运行轮次时执行一次。
- `defaultTracked` 只在当前没有追踪任务时生效，不覆盖玩家选择。

### 7.3 阶段定义

```csharp
[Serializable]
public sealed class WorldQuestStageDefinition
{
    [SerializeField] private string stageId;
    [SerializeField] private string title;
    [SerializeField, TextArea(1, 4)] private string objectiveSummary;
    [SerializeField, TextArea(1, 4)] private string activeReminderText;
    [SerializeField] private WorldQuestObjectiveCompletionMode completionMode;
    [SerializeField] private List<WorldQuestObjectiveDefinition>
        objectives = new();
    [SerializeField] private List<WorldQuestEffectDefinition>
        onEnterEffects = new();
    [SerializeField] private List<WorldQuestEffectDefinition>
        onCompleteEffects = new();
    [SerializeField] private List<WorldQuestStageTransitionDefinition>
        transitions = new();
}
```

规则：

- 每个阶段至少有一个目标。
- `All`：全部非可选目标完成后阶段完成。
- `Any`：任意一个目标完成后阶段完成，其他目标立即停止计数。
- `onEnterEffects` 在进入阶段的同一事务执行。
- `onCompleteEffects` 在离开阶段前执行。
- 非最终阶段必须至少有一个 `transition` 能在验证样例中命中。
- 最终阶段的 `transitions` 允许为空；为空表示进入交付或自动结算。

### 7.5 阶段转移

```csharp
[Serializable]
public sealed class WorldQuestStageTransitionDefinition
{
    [SerializeField] private string transitionId;
    [SerializeField] private int priority;
    [SerializeField] private WorldQuestConditionSet conditions;
    [SerializeField] private string requiredChoiceId;
    [SerializeField] private string targetStageId;
}
```

精确规则：

1. 阶段完成后筛选条件为真的转移。
2. `requiredChoiceId` 非空时，还必须等于本阶段记录的 `SelectedChoiceId`。
3. 按 `priority` 降序，再按资源中的序号升序。
4. 选择第一条命中的转移。
5. `targetStageId` 为空表示当前阶段是最终阶段，进入交付/结算。
6. 没有任何转移命中且列表不为空时，事务失败，任务保持原进度并记录错误。
7. 验证器必须拒绝形成阶段循环的定义。

### 7.6 结局定义

```csharp
[Serializable]
public sealed class WorldQuestOutcomeDefinition
{
    [SerializeField] private string outcomeId;
    [SerializeField] private int priority;
    [SerializeField] private bool isDefault;
    [SerializeField] private string choiceLabel;
    [SerializeField, TextArea(2, 5)] private string resolutionText;
    [SerializeField] private WorldQuestConditionSet selectionConditions;
    [SerializeField] private WorldQuestConditionSet turnInConditions;
    [SerializeField] private List<WorldQuestEffectDefinition> effects = new();
}
```

规则：

- 每条任务至少有一个结局。
- `selectionConditions` 决定该结局是否成为候选。
- `turnInConditions` 在玩家确认交付时检查当前 NPC、地点和世界状态；自动结算任务必须为空条件集。
- `ManualNpc` 可以有多个符合条件的结局，由玩家在交付对话中选择。
- `AutoOnFinalStage` 必须保证任何可达状态下只会有一个符合条件的结局。
- `isDefault` 在每条任务中必须恰好有一个。
- 手动交付必须传入显式 `OutcomeId`；UI 在只有一个候选时仍传入该候选 ID。
- 传入的 `OutcomeId` 必须存在、`selectionConditions` 为真且 `turnInConditions` 为真。

## 8. 存档层数据结构

### 8.1 状态枚举

枚举值顺序固定：

```csharp
public enum WorldQuestStatus
{
    Locked = 0,
    Available = 1,
    Active = 2,
    Suspended = 3,
    ReadyToTurnIn = 4,
    Completed = 5,
    Failed = 6,
    Cancelled = 7
}
```

定义：

| 状态 | 是否接收进度事件 | 是否显示NPC标记 | 是否终态 |
| --- | --- | --- | --- |
| `Locked` | 否 | 否 | 否 |
| `Available` | 否 | 发布者显示 `!` | 否 |
| `Active` | 是 | 否 | 否 |
| `Suspended` | 否 | 否 | 否 |
| `ReadyToTurnIn` | 否 | 交付者显示 `?` | 否 |

### 8.5 重复任务重置

`Never`：

- `Completed`、`Failed`、`Cancelled` 永久保持终态。

`Daily`：

- `NextAvailableWorldHour` 设为下一自然日开始：

```text
((LastCompletedWorldHour / 24) + 1) * 24
```

- 世界小时达到该值后，终态进入 `Available`。

`CooldownHours`：

- `NextAvailableWorldHour = LastCompletedWorldHour + cooldownHours`。
- 世界小时达到该值后，终态进入 `Available`。

任务进入 `Failed` 或 `Cancelled` 时，用 `LastUpdatedWorldHour` 代替 `LastCompletedWorldHour` 计算 `NextAvailableWorldHour`。

重复重置只清理当前轮次数据，不撤销过去写入的世界事实和对其他任务造成的影响。需要撤销的内容必须由新轮次效果显式覆盖。

### 9.4 可用性变化

初始化、读档、世界事实变更、任务终态变更、世界日变化后必须重算可用性：

- `Locked` 且条件为真：
  - 不论开始模式均先进入 `Available`。
  - 本轮所有可用性评估完成后，`AutoActivate` 任务再按固定顺序执行接取事务。
- `Available` 后条件变为假：回到 `Locked`，前提是尚未接受且定义不是重复任务等待期。
- `Active`、`Suspended`、`ReadyToTurnIn` 不因可用条件变假而自动改变；必须由显式效果中断、失败或取消。
- `Completed`、`Failed`、`Cancelled` 只按重复策略进入新一轮；`Never` 永不重开。

### 10.4 参与者要求

- `Any`：不检查参与者。
- `PlayerParty`：事件必须 `CreditedToPlayerParty == true`。
- `Protagonist`：事件必须 `ProtagonistParticipated == true`。
- 非战斗事件如配置 `Protagonist`，其 `ActorPersistentId` 必须等于 `GameData.ProtagonistPersistentId`。
- `DefeatCard` 默认必须使用 `Protagonist`；设计者显式改为其他值时验证器发出警告但不阻止。

### 10.5 进度计算

- `AddEventAmount`：

```text
new = min(requiredAmount, old + event.Amount)
```

- `SetToEventAmount`：

```text
new = clamp(event.Amount, 0, requiredAmount)
```

- `SetToCurrentSnapshot`：
  - `OwnCardCount`、`CurrencyBalance` 从正式库存重新计算。
  - `ProtagonistLevel` 读取当前主角等级。
  - `WorldDayReached` 读取当前世界日。
  - 其他目标配置该模式属于验证错误。

进度只增不减的目标：除 `OwnCardCount` 和 `CurrencyBalance` 外全部只增不减。库存类目标允许因物品减少重新变为未完成，但阶段一旦已经成功离开，不回退阶段。

### 11.4 各效果的精确行为

- `GrantCard`
  - 通过 `BackpackService` 的正式入包接口增加卡牌。
  - 同类型卡牌遵循背包现有合并规则。
  - 背包容量不足时整个任务事务失败，不得只发放部分奖励。
  - 发放奖励本身不得再次产生 `CardObtained` 任务事件，防止奖励递归推进任务。
- `GrantProtagonistExperience`
  - 调用 `ProtagonistProgressionService.TryGrantExperience`。
  - 升级结算在同一事务内完成。
  - 由效果造成的升级不额外报告 `ProtagonistLevelChanged`，事务末尾统一重新评估快照目标。
- `SetWorldFact*`
  - 目标事实不存在时创建，存在时要求类型一致。
  - 类型不一致视为事务验证失败。
- `IncrementWorldFactInt`
  - 不存在的事实按整数0创建。
  - 使用 `checked` 算术；溢出时事务失败并回滚。
- `MakeQuestAvailable`
  - 目标必须满足 `hardStartConditions`，否则事务失败。
  - 设置目标状态的 `AvailabilityOverride=true`。
  - 仅允许目标从 `Locked` 进入 `Available`。
  - 目标已是 `Available`、`Active`、`Suspended` 或 `ReadyToTurnIn` 时返回成功但不修改。
  - 目标是终态时不修改；是否可重开由重复策略处理。
- `ActivateQuest`
  - 允许目标状态为 `Locked` 或 `Available`。
  - 忽略目标的 `startMode`，但仍必须满足目标任务 `hardStartConditions`。
  - 创建新运行轮次，进入指定阶段或入口阶段，执行目标任务的接取效果和阶段进入效果。
  - 目标已处于进行态时视为幂等成功，不重新执行进入效果。
  - 目标是终态且未达到重复任务重开条件时事务失败。
- `SuspendQuest`
  - 只允许目标为 `Active` 或 `ReadyToTurnIn`。
  - 保存原状态到 `SuspendedFromStatus`，设置 `Status=Suspended` 和 `StatusReasonId=reasonId`。
  - 目标已经 `Suspended` 时，如果原因相同则幂等成功；原因不同则事务失败。
- `ResumeQuest`
  - 只允许目标为 `Suspended`。
  - 恢复为 `SuspendedFromStatus`，清空 `SuspendedFromStatus` 和 `StatusReasonId`。
  - 不重置阶段、进度和已选分支。
- `FailQuest`
  - 允许目标为 `Available`、`Active`、`Suspended` 或 `ReadyToTurnIn`。
  - 设置 `Status=Failed`、`StatusReasonId=reasonId`，保留最后阶段和进度用于日志/UI。
  - 已失败且原因相同视为幂等成功；其他终态不允许转换。
- `CancelQuest`
  - 行为与失败相同，但目标状态写为 `Cancelled`。
  - `Cancelled` 表示因世界变化而不再成立，不表示玩家失败。
- `TrackQuest`
  - 目标必须是 `Available`、`Active`、`Suspended` 或 `ReadyToTurnIn`。
  - 写入 `GameData.TrackedWorldQuestId`。
- `ShowNotification`
  - 只记录到事务的提交后通知队列。
  - 事务成功并完成内存提交后才显示；事务失败时不显示。

### 11.5 幂等键

每个效果的执行键固定为：

```text
{sourceQuestId}:{sourceRunNumber}:{sourceScopeId}:{effectId}
```

`sourceScopeId` 的取值：

- 接取效果：`accept`
- 阶段进入：`stage-enter:{stageId}`
- 阶段完成：`stage-complete:{stageId}`
- 结局效果：`outcome:{outcomeId}`

执行成功后把键写入源任务状态的 `AppliedOperationIds`。已存在的键直接跳过并返回成功。效果事务回滚时不得留下该键。

## 12. 状态机与合法转换

### 12.1 状态转换矩阵

| 当前状态 | 允许目标状态 | 唯一触发方式 |
| --- | --- | --- |
| `Locked` | `Available` | 可用条件满足或 `MakeQuestAvailable` |
| `Locked` | `Active` | `ActivateQuest` |
| `Available` | `Active` | 玩家接取、自动接取或 `ActivateQuest` |
| `Available` | `Failed` | `FailQuest` |
| `Available` | `Cancelled` | `CancelQuest` |
| `Active` | `Active` | 阶段完成后进入下一阶段 |
| `Active` | `ReadyToTurnIn` | 进入手动交付阶段并完成其目标 |
| `Active` | `Completed` | 自动结算结局 |
| `Active` | `Suspended` | `SuspendQuest` |
| `Active` | `Failed` | `FailQuest` |
| `Active` | `Cancelled` | `CancelQuest` |
| `Suspended` | `Active` | `ResumeQuest` 且原状态为 `Active` |
| `Suspended` | `ReadyToTurnIn` | `ResumeQuest` 且原状态为 `ReadyToTurnIn` |
| `Suspended` | `Failed` | `FailQuest` |
| `Suspended` | `Cancelled` | `CancelQuest` |
| `ReadyToTurnIn` | `Completed` | 玩家选择有效结局并交付 |
| `ReadyToTurnIn` | `Suspended` | `SuspendQuest` |
| `ReadyToTurnIn` | `Failed` | `FailQuest` |
| `ReadyToTurnIn` | `Cancelled` | `CancelQuest` |
| `Completed` | `Available` | 重复策略到期后新一轮 |
| `Failed` | `Available` | 重复策略到期后新一轮 |
| `Cancelled` | `Available` | 重复策略到期后新一轮 |

矩阵外的转换一律返回 `InvalidStateTransition`，不修改任何数据。

### 12.2 接取流程

`TryAccept(questId)` 的固定步骤：

1. 读取任务定义和状态。
2. 要求状态为 `Available`。
3. 重新计算 `hardStartConditions` 和 `acceptConditions`，任一不满足则失败。
4. `RunNumber += 1`。
5. 状态设为 `Active`，阶段设为 `entryStageId`。
6. 清空旧进度、分支、结局、原因和幂等键。
7. 记录 `AcceptedWorldHour` 和 `LastUpdatedWorldHour`。
8. 执行 `onAcceptEffects`。
9. 执行入口阶段 `onEnterEffects`。
10. 对入口阶段的快照型目标立即求值。
11. 若入口阶段立即完成，按第13章规则推进一次。
12. 事务成功后发布状态变化事件并保存。

### 12.3 阶段完成流程

当当前阶段满足完成模式时：

1. 执行当前阶段 `onCompleteEffects`。
2. 若转移数组为空，当前阶段必须是最终阶段，直接执行步骤5。
3. 若转移数组非空，按优先级降序、数组索引升序筛选并选择第一条条件满足的转移；零条命中属于定义错误。
4. 写入新 `ActiveStageId`，初始化该阶段进度，执行其 `onEnterEffects`。
5. 最终阶段完成时：
   - `turnInMode=ManualNpc`：状态设为 `ReadyToTurnIn`。
   - `turnInMode=AutoOnFinalStage`：立即按第14章选择并结算结局。
6. 一个外部事件最多完成一个阶段；新阶段即使快照目标已经满足，也要等下一次显式重新评估调用。

### 12.4 终态规则

- `Completed`、`Failed`、`Cancelled` 为终态。
- 终态不得被普通事件推进。
- 终态状态只通过重复策略进入下一轮 `Available`。
- 结局、最终原因、最后阶段和最后进度永久保存在该轮状态中。
- 同一任务只保存当前/最近一轮的完整状态；历史统计保存于 `CompletionCount`，不保存每轮详细日志。

## 13. 任务引擎

### 13.1 初始化

`WorldQuestRuntime.Initialize(GameData gameData)` 固定执行：

1. 验证 `gameData` 非空。
2. 执行 V1→V2 存档迁移。
3. 从 `Resources/WorldQuests` 加载全部定义。
4. 按 `questId` 升序建立只读注册表。
5. 运行定义验证；存在 Error 时中止进入游戏并在开发版本显示错误列表。
6. 为没有状态的定义建立 `Locked` 状态。
7. 清理指向不存在任务的 `TrackedWorldQuestId`。
8. 处理到期的重复任务。
9. 重新评估全部可用条件。
10. 对 `startMode=AutoActivate` 且为 `Available` 的任务按 `priority` 降序、`questId` 升序自动接取。
11. 发布一次 `RuntimeInitialized`，不逐条弹出通知。

初始化只能执行一次；重复调用返回现有实例，不重复应用效果。

### 13.2 事件处理算法

`ReportEvent(WorldQuestEvent evt)` 固定执行：

1. 验证事件字段及 `EventId`。
2. 若 `EventId` 已存在于 `GameData.ProcessedWorldQuestEventIds`，返回幂等成功。
3. 取得所有 `Active` 任务，按 `priority` 降序、`questId` 升序排列。
4. 对每条任务只读取 `ActiveStageId` 对应的阶段。
5. 对阶段中每个目标执行事件类型、目标、场景、方向和参与者匹配。
6. 在事务副本中更新进度。
7. 判断阶段完成条件。
8. 已完成时仅推进一次阶段。
9. 全部任务处理完后执行关联任务重新评估。
10. 事务提交后记录该事件 ID，发布合并后的状态变化事件并请求保存。

一个事件可以推进多条任务，但不能让同一任务跨越两个阶段。

### 13.3 阶段完成模式

- `All`：阶段内每个 `optional=false` 的目标均完成。
- `Any`：至少一个 `optional=false` 的目标完成。
- 阶段目标数组不得为空。纯对话阶段使用 `TalkToNpc`，有选项的对话阶段使用 `DialogueChoice`。

### 13.4 可用性重新评估

以下时机必须调用 `ReevaluateAvailability()`：

- 运行时初始化完成迁移后。
- 世界事实改变后。
- 任一任务进入终态后。
- 主角等级改变后。
- 世界日期改变后。
- 关联效果事务执行完后。

评估规则：

1. 只检查 `Locked` 状态和已到重复重开时间的终态。
2. `hardStartConditions` 必须为真；此外 `availabilityConditions` 为真或 `AvailabilityOverride=true` 时进入 `Available`。
3. `hardStartConditions` 变假，或 `availabilityConditions` 变假且没有 Override 时，`Available` 返回 `Locked`；已经接取的任务不自动中断。
4. 进行中任务是否中断只能由显式 `SuspendQuest`、`FailQuest` 或 `CancelQuest` 效果决定。
5. 自动接取任务在本轮重新评估完成后统一接取，禁止评估过程中递归接取。

### 13.5 联动收敛

一次事务中的任务联动使用队列处理：

1. 把效果直接修改的 QuestId 和 WorldFactId 加入脏集合。
2. 按 QuestId 升序重新评估受影响任务。
3. 新产生的效果继续入队。
4. 每个幂等键最多执行一次。
5. 队列为空时结束。
6. 单事务最多处理512个状态/效果操作；超过上限判定为循环配置，整个事务回滚。

验证器仍必须阻止任务可用性依赖和直接激活关系形成静态环。512上限用于防止由运行时事实组合形成的动态环。

## 14. 结局、分支与任务关联

### 14.1 结局候选计算

`GetEligibleOutcomes(questId)` 只接受 `ReadyToTurnIn` 或正在自动结算的任务，计算步骤固定为：

1. 取得任务定义的 `outcomes`。
2. 按数组顺序评估每个结局的 `conditions`。
3. 保留条件为真的结局。
4. 按 `priority` 降序、数组索引升序排序。

结果处理：

- `turnInMode=AutoOnFinalStage`：必须只有一个最高优先级结局；并列视为定义错误。
- `turnInMode=ManualNpc` 且只有一个候选：UI 显示该结局的确认按钮。
- `turnInMode=ManualNpc` 且多个候选：UI 按排序结果显示全部可选结局。
- 零个候选：返回 `NoEligibleOutcome`，保持原状态并输出配置错误。

### 14.2 手动交付

`TryTurnIn(questId, outcomeId)` 固定要求：

- 状态为 `ReadyToTurnIn`。
- `outcomeId` 存在于当前候选集合；只有一个候选时调用方也必须显式传入该 ID。
- 当前交付 NPC 必须位于任务的 `turnInNpcIds`，且结局定义的 `turnInConditions` 为真。

成功后依次：

1. 执行结局效果。
2. 写入 `OutcomeId`。
3. 写入 `Status=Completed`。
4. `CompletionCount += 1`。
5. 写入 `LastCompletedWorldHour`、`LastUpdatedWorldHour`。
6. 依据重复策略计算 `NextAvailableWorldHour`。
7. 重新评估受影响任务。
8. 提交事务、显示结局通知并保存。

### 14.3 阶段内选择

需要在任务中途分支时，使用 `DialogueChoice` 目标：

- `targetId` 为 `ChoiceGroupId`。
- 玩家点击选项后报告 `DialogueChoiceSelected`。
- 匹配成功时把选择 ID 写入 `SelectedChoiceId`。
- 后续转移条件使用 `SelectedChoiceEquals`。
- 同一运行轮次只允许第一次选择生效；再次提交不同选择返回 `ChoiceAlreadyLocked`。
- 任务进入下一轮时清空该字段。

本轮不支持回溯选择。需要允许重新选择的内容必须设计为尚未完成阶段内的普通 UI 预览，只有最终确认才报告事件。

### 14.4 任务之间的确定性联动

任务 A 影响任务 B 时只允许以下方式：

1. A 的结局设置世界事实，B 的可用/转移/结局条件读取事实。
2. A 的效果直接对 B 执行可用、激活、中断、恢复、失败或取消。
3. B 的条件读取 A 的 `Status` 或 `OutcomeId`。

选择规则：

- 长期世界变化使用世界事实。
- “某结局后出现新任务”优先使用 B 的条件，不使用 A 直接激活。
- “必须立刻中断另一任务”使用 A 的 `SuspendQuest`、`FailQuest` 或 `CancelQuest`。
- “必须立即开始并绕过普通接取入口”才使用 `ActivateQuest`。

任何任务定义不得直接调用其他任务脚本，也不得通过场景对象名称查找另一任务。

### 14.5 中断、失败和取消的产品语义

- `Suspended`
  - 暂时不能推进。
  - 保留进度，任务日志显示中断原因。
  - 原因解除后只能由 `ResumeQuest` 恢复。
- `Failed`
  - 玩家未达成任务目标或触发明确失败条件。
  - 当前轮结束，可以影响后续任务和结局。
- `Cancelled`
  - 世界状态使任务内容不再成立，例如目标 NPC 死亡或阵营已消失。
  - 不计作玩家失败，但当前轮同样结束。

任务失败与取消不会自动回收此前获得的普通物品。需要回收时必须在相应效果中增加明确的物品扣除效果；本轮没有该效果类型，因此本轮任务不得设计自动回收物品。

## 15. 原子事务与保存一致性

### 15.1 事务边界

以下操作必须使用 `WorldQuestTransaction`：

- 接取任务。
- 报告并处理正式游戏事件。
- 完成阶段。
- 选择并提交结局。
- 执行任何任务效果。
- 重复任务重开。
- 存档迁移。

### 15.2 事务步骤

```text
创建事务
→ 验证定义、状态和外部资源
→ 创建受影响数据快照
→ 在工作副本中更新目标/状态
→ 执行效果
→ 重新评估关联任务直至收敛
→ 再次验证全部不变量
→ 提交内存数据
→ 发布状态变化事件
→ 显示通知
→ 请求磁盘保存
```

任何验证或执行步骤失败时：

```text
恢复快照
→ 丢弃通知与状态变化事件
→ 返回错误码
→ 输出一次带事务 ID 的错误日志
```

### 15.3 必须快照的数据

事务开始时复制以下受影响数据：

- `GameData.WorldQuests`
- `GameData.WorldFacts`
- `GameData.ProcessedWorldQuestEventIds`
- `GameData.TrackedWorldQuestId`
- `GameData.BackpackEntries`
- `GameData.ProtagonistProgression`
- 本事务将修改的其他现有永久字段

第一版允许复制上述完整集合，不要求差量快照。事务对象不得复制或销毁场景 GameObject。

### 15.4 外部资源预验证

执行效果前必须确认：

- 奖励 CardDefinition 存在。
- 背包有足够容量。
- 主角成长服务已初始化。
- 目标 QuestDefinition、StageId、WorldFact 类型存在或可合法创建。
- 所有状态转换合法。

预验证成功不代表跳过执行期异常处理；任何执行期异常仍必须回滚。

### 15.5 通知和运行时事件

运行时只在事务提交后发布：

```csharp
public event Action<WorldQuestChangedEvent> QuestChanged;
public event Action<WorldFactChangedEvent> WorldFactChanged;
public event Action<string> TrackedQuestChanged;
public event Action<WorldQuestNotification> NotificationRequested;
```

同一任务在单事务内变化多次时，只发布一个 `QuestChanged`，其中包含事务开始前状态和最终状态。UI 不监听内部步骤。

### 15.6 磁盘保存

任务事务成功后调用统一 `SaveRequestService.RequestSave(SaveReason.QuestStateChanged)`。同一帧的多个请求合并为一次保存。

`SaveSystem` 必须改为原子写入：

1. 序列化到 `save.tmp`。
2. 写入并关闭文件流。
3. 已有正式存档时，用 `File.Replace(save.tmp, save.json, save.bak)`。
4. 没有正式存档时，用 `File.Move(save.tmp, save.json)`。
5. 启动读取失败时先读取 `save.bak`。

不得继续用 `File.WriteAllText` 直接覆盖正式存档。场景切换和退出游戏必须等待当前保存任务完成。

## 17. NPC 对话接入

### 17.1 禁止硬编码

`DialogueManager` 不得包含 `story_riverbend_whispering_forest_01`、NPC 对应任务 ID、任务阶段编号或任务奖励文本。它只向运行时提交 `npcId + locationId`，并渲染返回的交互项。

### 17.2 NPC 交互排序

`ResolveNpcInteraction(npcId, locationId)` 搜集该 NPC 当前关联任务，按以下顺序返回：

1. 可在此交付的 `ReadyToTurnIn`
2. 可在此接取的 `Available`
3. 当前阶段要求与该 NPC 对话的 `Active`
4. 该 NPC 配置了进行中提醒的 `Active`
5. 最近一次由该 NPC 交付且配置了结局回顾的终态

同类按任务 `priority` 降序、`questId` 升序排列。存在多个交互项时，先显示任务标题列表，玩家选择后进入具体对话。

### 17.3 NPC 标记

- 存在可交付任务：青色 `?`
- 否则存在可接任务：金色 `!`
- 两者都不存在：不显示任务标记
- 标记内容在 `QuestChanged` 后重算

NPC 的普通对话仍由现有配置处理，任务系统返回空列表时回退普通对话。

### 17.4 对话按钮行为

- 接取按钮调用 `TryAccept`，成功后才关闭接取界面。
- 阶段选择按钮只在玩家最终确认时报告 `DialogueChoiceSelected`。
- 交付按钮必须传入明确 `outcomeId`。
- 操作失败时保持对话界面打开，显示面向玩家的本地化错误文本。

## 20. 存档版本与迁移

### 20.1 版本号

```csharp
public const int CurrentWorldQuestStateVersion = 2;
```

加载顺序固定为：

1. 反序列化 `GameData`。
2. 读取 `WorldQuestStateVersion`；字段缺失按0处理。
3. 依次执行每个版本迁移，不允许跨版本跳过。
4. 每个迁移在内存副本上执行。
5. 全部迁移和验证成功后才替换当前 `GameData`。
6. 立即用第15.6节的原子保存方式写回 V2 存档。

版本高于客户端支持版本时拒绝加载，显示“存档由更新版本创建”，不得尝试降级读取。

V1 与 V2 的 `WorldQuestStatus` 数值顺序不同，禁止把 V1 JSON 直接反序列化到 V2 枚举。迁移器必须先从原始 JSON 额外反序列化以下只读 DTO：

```csharp
public enum LegacyWorldQuestStatusV1
{
    Available = 0,
    Active = 1,
    ReadyToTurnIn = 2,
    Completed = 3
}

[Serializable]
public sealed class LegacyWorldQuestStateDataV1
{
    public string QuestId;
    public LegacyWorldQuestStatusV1 Status;
    public int ObjectiveIndex;
    public int CurrentAmount;
    public bool AcceptanceRewardClaimed;
    public bool CompletionRewardClaimed;
}

[Serializable]
public sealed class LegacyWorldQuestEnvelopeV1
{
    public int WorldQuestStateVersion;
    public List<LegacyWorldQuestStateDataV1> WorldQuests;
}
```

加载 V1 时流程固定为：原始 JSON 反序列化当前 `GameData` 以保留其他字段；再反序列化 `LegacyWorldQuestEnvelopeV1`；丢弃当前 `GameData.WorldQuests` 中被错误枚举解释的数据；从 Legacy DTO 逐条创建 V2 状态。

### 20.2 V1→V2 的“林间异响”映射

当前 V1 的 `story_riverbend_whispering_forest_01` 状态迁移为以下固定结构：

| V1 数据 | V2 状态 |
| --- | --- |
| 没有该任务状态 | 新建 `Locked`，再由可用条件评估 |
| `Status=Available` | `Status=Available`，`ActiveStageId` 为空，忽略旧索引和进度 |
| `Status=Active, ObjectiveIndex=0` | `Status=Active`，`ActiveStageId=prepare_supplies`，目标 `buy_food` 继承原 `CurrentAmount` |
| `Status=Active, ObjectiveIndex=1` | `Status=Active`，`ActiveStageId=travel_to_forest`，目标继承原 `CurrentAmount` |
| `Status=Active, ObjectiveIndex=2` | `Status=Active`，`ActiveStageId=investigate_forest`，目标继承原 `CurrentAmount` |
| `Status=Active, ObjectiveIndex=3` | `Status=Active`，`ActiveStageId=report_to_chief`，目标继承原 `CurrentAmount` |
| `Status=ReadyToTurnIn` | `Status=ReadyToTurnIn`，`ActiveStageId=report_to_chief`，该阶段目标写为完成 |
| `Status=Completed` | `Status=Completed`，`ActiveStageId=report_to_chief`，`OutcomeId=threat_reported` |

额外规则：

- V1 已接取任务写 `RunNumber=1`。
- V1 已完成任务写 `RunNumber=1`、`CompletionCount=1`。
- 不存在的时间字段写 `-1`，不得用当前时间伪造历史。
- `AcceptanceRewardClaimed=true` 时写入全部接取奖励的 `accept` 幂等键；为 false 时不写。
- `CompletionRewardClaimed=true` 时写入 `outcome:threat_reported` 的全部结局奖励幂等键；为 false 时不写。
- `Status=Completed` 但 `CompletionRewardClaimed=false` 时，首次加载 V2 后通过恢复事务发放一次完成奖励，再写入幂等键。
- `Status=ReadyToTurnIn` 但 `CompletionRewardClaimed=true` 属于非法组合，迁移失败并保留原始存档。
- 若 V1 阶段索引越界，迁移失败并保留原始存档，不静默重置任务。

### 20.3 旧 QuestManager 数据

- 现有 `Assets/StackCraft/Resources/Quests` 下66个教学/里程碑资源不迁移。
- 旧 `QuestManager` 的存档字段原样保留。
- 本轮不得删除旧资源、场景引用或旧 UI 数据读取。
- 新建的主线、支线、NPC 任务和委托一律使用 World Quest V2。
- 后续迁移旧任务必须另立技术规格和独立存档版本。

### 20.4 存档不变量

加载与提交前必须验证：

- 每个 `QuestId` 最多一条状态。
- `Active`、`Suspended`、`ReadyToTurnIn` 必须有有效 `ActiveStageId`。
- `Completed` 必须有有效 `OutcomeId`。
- 非 `Suspended` 状态的 `SuspendedFromStatus` 必须为空。
- `Suspended`、`Failed`、`Cancelled` 必须有有效 `StatusReasonId`；其他状态必须为空。
- 目标进度键必须属于当前阶段；迁移历史例外必须在迁移结束前清理。
- 进度范围为0到 `requiredAmount`。
- `RunNumber >= CompletionCount >= 0`。
- `AppliedOperationIds` 内无重复项。
- WorldFactId 唯一且类型有效。
- `ProcessedWorldQuestEventIds` 无重复项且数量不超过2048。

违反不变量时停止加载 V2 数据并尝试 `.bak`，不得自动删除异常条目继续游戏。

- 任务没有摘要。

## 25. 确定性与容量限制

### 25.1 固定处理顺序

- 任务：`priority` 降序，再按 QuestId Ordinal 升序。
- 阶段目标：资源数组顺序。
- 阶段转移：`priority` 降序，再按资源数组顺序。
- 结局：`priority` 降序，再按资源数组顺序。
- 效果：资源数组顺序。
- 同一事务的通知：效果实际提交顺序。
- 存档列表：保存前按 ID 升序整理，保证 diff 和测试稳定。

禁止依赖 `Dictionary`、`HashSet` 或 `Resources.LoadAll` 的枚举顺序决定游戏结果。

### 25.2 硬上限

| 项目 | 上限 | 超出行为 |
| --- | ---: | --- |
| 已注册 V2 任务 | 500 | 验证 Error |
| 同时进行态任务 | 50 | 新接取返回 `ActiveQuestLimitReached` 并显示任务上限提示 |
| 每任务阶段 | 32 | 验证 Error |
| 每阶段目标 | 16 | 验证 Error |
| 每阶段转移 | 16 | 验证 Error |
| 每任务结局 | 8 | 验证 Error |
| 每条件集合条件 | 32 | 验证 Error |
| 每个效果列表 | 32 | 验证 Error |
| 单事务联动操作 | 512 | 回滚 |
| 单状态幂等键 | 256 | 验证/运行错误，不删除未归档键 |

任务进入终态且确认永不重复时，允许保存压缩器只保留接取与结局效果幂等键；本轮不实现该压缩器，因此不得自动删除键。

### 25.3 性能要求

- `ReportEvent` 只遍历进行态任务，不遍历全部500条定义。
- 运行时为事件类型建立“进行中目标”索引；阶段变化时更新索引。
- 条件读取 WorldFact、任务状态和定义使用运行时字典索引。
- 单次事件处理目标时间低于1毫秒（Editor Development Build、50条进行态任务、普通桌面 CPU）。
- UI 不得每帧重建任务列表，只响应运行时提交后事件。
- 任何性能优化不得改变第25.1节顺序。

- `Info`：接取、阶段变化、结局、重复重开。
- `Warning`：合法但幂等的重复事件、备份存档恢复、迁移冲突采用明确优先规则。
- `Error`：事务回滚、资源缺失、非法状态转换、定义运行时歧义。
- `Fatal`：定义注册表无效、主存档和备份均无法读取、高版本存档。

### 26.3 发布版本行为

- 单条任务定义在构建前已验证，因此运行时遇到定义 Error 视为不可恢复故障。
- 任务事务故障不得让游戏继续保存部分状态。
- 存档无法读取时保留原文件，不自动创建新存档覆盖。
- UI 操作失败后保持原界面与可重试状态。
